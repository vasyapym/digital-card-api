# Obsidian Second Brain

My Obsidian vault, searchable from any device by keywords and by meaning. It runs on free tiers for $0/month. Embeddings are computed in CI by a pinned local model, so notes never reach an AI provider.

**Status:** the indexer is live (M0–M2, `v1.0.1`). The passphrase-gated reader at `/brain` is next (M3). Until it ships, every `BRAIN_*` flag is off and the deployment serves only my [digital card](#the-card).

Live: https://vasyapym.onrender.com · GraphQL sandbox: https://vasyapym.onrender.com/graphql · Health: https://vasyapym.onrender.com/health

## How it works

```
 private vault repo                         this repo (pinned tag)
 Obsidian Git pushes *.md                   ├ indexer CLI
 workflow runs the indexer ◀── checkout ─── ├ embedding (pinned model)
 on the GitHub runner                       └ card + /brain (NestJS)
           │                                            │
           │ upsert (brain_* role)                      │ deploy
           ▼                                            ▼
   Neon Postgres ◀────────── SELECT only ─────── Render web service
   brain_* tables                                (free, kept awake)
```

1. Obsidian Git pushes to a private vault repo. Its workflow checks out this repo at a pinned tag and runs the indexer on the runner.
2. Indexing is incremental against `brain_meta.last_indexed_sha`. Changed notes are parsed (frontmatter, tags, aliases, wiki-links) and chunked by heading (~400 tokens).
3. Chunks are embedded on the runner by a sha256-pinned `Xenova/multilingual-e5-small` (int8 ONNX, 384-dim).
4. Results are upserted into Neon through a role limited to `brain_*` tables. Full rebuilds never truncate, so search never sees an empty index and a cancelled run heals on the next one.
5. `/brain` (M3) will serve hybrid search behind a passphrase: Postgres full-text plus pgvector, merged with reciprocal-rank fusion. The reader is read-only; the vault stays the only place notes are written.

## Design decisions

- **Public code, private vault.** Nothing from the vault lives here. Fixtures are synthetic, URLs use opaque ids, and the vault workflow greps the pinned code against a private denylist on every run.
- **Logs carry counts and error codes only.** They never contain messages, paths or note text.
- **Least privilege.** The only CI secret is a DB role scoped to `brain_*`. The web app only SELECTs vault data, and Render holds no GitHub credential.
- **The model is code, not config.** Vectors are only comparable within one model and quantisation. The Docker build downloads the pinned files and fails on a checksum mismatch. Keyword-only search (`BRAIN_SEMANTIC=false`) is a supported mode.
- **Hand-reviewed migrations.** Prisma can't represent the generated `tsv` column, the HNSW index or the GIN index, so an autogenerated migration would drop them. Brain migrations are created with `--create-only` and reviewed by hand. `migrations.lint.spec.ts` fails the build if a later migration touches those objects, and `brain_*` tables are accessed through raw SQL only.

## The card

This repository started as `digital-card-api`, the read-only GraphQL API behind my digital business card. The card still runs at the links above. With `BRAIN_ENABLED=false` (the default), the app behaves exactly as it did before the brain existed.

## Self-host

- Today (M0–M2, tag `v1.0.1`): your private vault repo runs this repo's indexer at a pinned tag → your own Postgres. The reader `/brain/*` is M3 — until then, SQL over `brain_*`.
- Workflow template: [docs/vault-index.workflow.yml](docs/vault-index.workflow.yml) → `<vault>/.github/workflows/second-brain-index.yml`, secret `BRAIN_DB_URL` (least-privilege DB role), optional `<vault>/.second-brain/config.json` (`excludeFolders`) and `denylist.txt`.
- Database: free Neon Postgres; `DATABASE_URL` (pooled) + `DIRECT_URL` (direct) → `npx prisma migrate deploy` — the first migration creates the `vector` extension.
- Web service (needed from M3): Render free, Docker runtime; every `BRAIN_*` flag off — the app is the card and nothing else.
- Card data: `src/data/profiles.data.ts` is the demo profile — replace it with your own (exactly one entry with `isPrimary: true`).

## Operations

- **Render:** free plan, Docker runtime. The health check `/health` is process-only and never touches Postgres. UptimeRobot pings `/graphql` every 5 min to keep the service awake.
- **Neon:** `DATABASE_URL` is the pooled connection and `DIRECT_URL` the direct one. Env is zod-validated at startup and fails fast.
- **Boot sequence:** `check-env → prisma migrate deploy → seed → server`. Any failing step stops the boot.

| Variable | Default | Meaning |
| --- | --- | --- |
| `BRAIN_ENABLED` | `false` | Master switch; `true` requires the two secrets below. |
| `BRAIN_PASSPHRASE_HASH` | – | argon2id hash of the access passphrase. |
| `BRAIN_SESSION_SECRET` | – | ≥32 chars, signs the session cookie. |
| `BRAIN_SEMANTIC` | `false` | Adds vector search on top of keyword search. |

Deploying with the brain disabled is the normal path. Migrations create empty `brain_*` tables, the model sits unused in the image, and no `/brain` route is registered.

**One-time Neon setup.** The first brain migration runs `CREATE EXTENSION IF NOT EXISTS vector;`. If the migration role doesn't own the database, run that statement once as the owner on the direct connection before the first deploy. Then create the `brain_indexer` role with grants on `brain_*` tables only. That way a leaked CI secret can't read or modify the card's tables.
