# Digital Card API

Read-only GraphQL API behind my digital business card: profile, links, skills (filterable by category), experience (computed `isCurrent` and `durationInMonths`), and projects.

Live: https://vasyapym.onrender.com — API sandbox: https://vasyapym.onrender.com/graphql — Health: https://vasyapym.onrender.com/health

## Stack

TypeScript · NestJS 11 · GraphQL (code-first, Apollo) · Prisma 6 · PostgreSQL (Neon) · Jest · Docker

## How it runs

- Render (free plan, Docker runtime, health check `/health`). Free instances sleep, so UptimeRobot keeps it warm with a HEAD request to `/graphql` every 5 minutes (DB-free, so Neon still scales to zero); `/health` stays process-only and `/health/db` is for manual checks only. `HEAD /` is also database-free.
- PostgreSQL is hosted on Neon. `DATABASE_URL` uses the pooled connection, `DIRECT_URL` the direct one (validated at startup with zod, fail-fast).
- Startup chain in the container: `check-env → prisma migrate deploy → seed → server`. Any failed step prevents boot.
- `src/data/profiles.data.ts` is the single source of truth for the card content.

## Second brain (M2 indexer)

- `src/second-brain/` — a private, read-only window over an Obsidian vault, built in milestones (M0 deps/flags, M1 migration, M2 indexer, M3 web). With `BRAIN_ENABLED=false` (the default) nothing registers and the card behaves exactly as before.
- The indexer is a standalone CLI (`dist/second-brain/indexer/cli.js`) run by a workflow in the private vault repo. The public repo never sees vault names or paths; fixtures are synthetic; logs print counts only.
- Embeddings come from a pinned, sha256-verified `Xenova/multilingual-e5-small`, baked into the image at build; the signature stored in `brain_meta` gates semantic search.
- Migration discipline: new migrations are created with `prisma migrate dev --create-only` and reviewed by hand; `migrations.lint.spec` fails the build if a later migration drops or alters the generated `tsv`, the HNSW or the tsv-GIN objects.
- No screenshots of real content, ever.

## Second brain (v1, M0/M1 — schema + model plumbing only)

A private, passphrase-gated notes search that ships inside this API. Milestones M0/M1 add
only the database schema, the embedding-model pin and two lint specs; there is no route,
no module and no UI yet.

### Environment flags

All flags default to **off**. With none of them set the deployed app behaves exactly as it
did before this change.

| Variable | Default | Meaning |
| --- | --- | --- |
| `BRAIN_ENABLED` | `false` | Master switch. When `true`, the two secrets below are required. |
| `BRAIN_PASSPHRASE_HASH` | – | argon2id hash (`$argon2id$…`) of the access passphrase. |
| `BRAIN_SESSION_SECRET` | – | ≥32 chars, signs the session cookie. |
| `BRAIN_SEMANTIC` | `false` | Vector search on top of keyword search. `false` = keyword-only, a fully supported mode. |

Env validation is fail-fast (`check-env` runs first in the container): `BRAIN_ENABLED=true`
without the two secrets aborts startup instead of serving an unprotected surface.

### Deploying with the brain disabled

The normal path. Deploy as usual with no `BRAIN_*` variables:

- `prisma migrate deploy` creates the `brain_*` tables (empty, unused — no behaviour change);
- the image contains the embedding model, but nothing loads it;
- no new routes, no new middleware, no extra queries.

Enabling later is a config change plus an indexing run, not a redeploy of different code.

### Migration discipline

- `prisma migrate deploy` applies committed SQL verbatim and never diffs — production is
  always safe.
- Future brain migrations are created with `prisma migrate dev --create-only` and reviewed
  by hand. Prisma cannot represent the generated `tsv` column or the `hnsw` index, so an
  unreviewed autogenerated migration will try to drop them.
- `src/second-brain/migrations.lint.spec.ts` fails the build if any migration created after
  the second-brain migration drops or alters `tsv`, `brain_chunks_tsv_gin` or
  `brain_chunks_emb_hnsw`. It is part of `npm test`, which runs inside the image build.
- The `brain_*` tables are read and written only through `$queryRaw` / `$executeRaw`; the
  Prisma models exist to keep the schema honest, not to be used by the client.

### One-time Neon setup (owner-run SQL)

The migration starts with `CREATE EXTENSION IF NOT EXISTS vector;`. If the migration role
is not the database owner, run this once as the project owner on the **direct**
(non-pooled) connection, before the first deploy:

    -- as the Neon owner role, on DIRECT_URL (not the pooled URL)
    CREATE EXTENSION IF NOT EXISTS vector;

If a separate application role is used, also grant it the usual object privileges:

    GRANT USAGE ON SCHEMA public TO <app_role>;
    GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO <app_role>;
    GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO <app_role>;

After that the extension already exists and the `IF NOT EXISTS` in the migration is a
no-op, so `prisma migrate deploy` succeeds with the ordinary role.

### Model pinning

The embedding model is a code constant in `src/second-brain/embedding/embedding.constants.ts`
(`Xenova/multilingual-e5-small`, int8 ONNX, 384-dim, e5 `query: ` / `passage: ` prefixes),
never an environment variable: vectors are only comparable within one model+quantisation.
`fetch-model.ts` runs in the Docker build stage, downloads the pinned files into
`/app/models`, verifies the sha256 of the ONNX graph and fails the build on mismatch.
Until `REVISION`/`ONNX_SHA256` are pinned to real values it prints the resolved commit and
digest and warns; set `BRAIN_MODEL_STRICT=1` in the build to make that state fatal.
